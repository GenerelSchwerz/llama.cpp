# CPU-assisted prefill partition

## Source-backed decision

Main sequential prompt rows currently receive zero `hybrid_rows` in `llama-context.cpp::process_ubatch`, although `ggml_backend_sched_hybrid_certificate_supported` accepts main sequential certificates. Widening this admission is insufficient: `moe-source-core.cu::allocate` reserves transfer payload for all selected distinct experts, which scales with the full prompt's expert coverage. The decode packet and its optional combined-body arithmetic must not become mandatory prefill admission.

Reuse `ggml_cuda_mmid_prefill_prepare`, `launch_range` and `finish` instead. They group the original input once, execute ordinary GGML matrix arithmetic against canonical resident or event-protected staged sources, and restore the original route order once. Extend this existing prepared consumer with an optional checked CPU-expert ownership table. A CPU cohort includes every original route to that expert; no model name, quantization list or fixed cohort size is required. GPU range launches skip CPU-owned cohorts and validate all GPU source slots before submitting that range. An explicit join copies only CPU-owned original routes from the existing synchronous CPU service's private result. Ownership and original IDs are retained in the prepared object, while CPU result memory remains borrowed through copy completion.

Keep the existing full-GPU prepare path unchanged. Zero only the partitioned prepared output before GPU arithmetic so skipped CPU rows cannot publish uninitialized data. GPU preparation/finish and CPU join are separate operations: the orchestrator can overlap CPU arithmetic with GPU waves, then fence both before public graph continuation. Preserve original post-operations and auxiliary routing readers in the original graph. A partial result is not successful graph publication.

The caller must retain the canonical source transaction, staging range, prepared grouping buffers and CPU output until the actual last copy/reader completes. Use existing ordered streams/events and shared worker execution control; no second residency authority or CPU pool. Cross-layer issuance and cache loans remain separate features and must share the same aggregate budget.
