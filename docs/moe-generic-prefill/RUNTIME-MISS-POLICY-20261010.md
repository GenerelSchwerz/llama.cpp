## Source inventory and design

- `ggml-cuda/moe-source-core.cu`: `build_plan` partitions distinct experts into resident, transferred and CPU classes. `allocate` currently reserves transfer scratch for the immutable fraction, so a larger dynamic fraction would overrun that reservation. `execute_cpu` calls the existing synchronous CPU region service. Replay already has a successful drain/publication boundary.
- `ggml-cpu/ggml-cpu.cpp`: the CPU region service has a compute boundary after binding and before scattering. Measure this boundary, including pool service, rather than GPU join waiting or lane acquisition.
- `moe-fidelity-config.h` and `ggml-backend.cpp`: process activation and explicit miss fraction are immutable. Keep explicit fractions immutable; add a separate hardware tuning selection.
- `ggml-moe-source-program.cpp`: graph cloning retains tensor dependencies and the private allocation graph. Rank evidence must come from a structurally validated scalar routing-weight tensor, never the ID column number. Preserve its storage until route publication.
- The graph certificate distinguishes independent rows from speculative windows but does not carry per-row request ownership for mixed speculative requests. Independent rows must make independent omission decisions. A single-sequence speculative window may aggregate the best expert rank. Mixed speculative requests must remain exact until the upstream request mapping can express this safely.
- The grouped CUDA context is the canonical per-device residency/resource owner. Hardware measurement state may live there but must not become another residency map or admission authority.

The read-only v0.1.42 reference uses CPU bytes/service time and measured link bandwidth, at most three updates after 48/96/96 windows, rounded to .05 and clamped to .10-.60. Its 1.85 multiplier, thresholds and clamp are empirical. Its fixed top10 rank assumption and default-on omission are unsuitable for the generic executor.

## Blocking approximation finding: prompt/generation provenance

The prototype is not ready to publish. The 2049-token prompt produces a 2048-row sequential prefill and a separate one-row call. In `flash-mtp-skip-23`, program3 (one epoch) omits123 routes in this final prompt row. Its existing certificate marks that row independent. Checking only row count/main-prefill does not establish generation provenance. Thus the earlier statement that prompt prefill remains exact is false for one-row prompt tails. All prototype approximation timings above include that defect and must not be promoted as valid decode-only comparisons. Exact and CPU-tuning-only controls still execute every route.

Source evidence:

- `llama_context::make_graph_execution_certificate` checks `ubatch_has_independent_rows` before sequential spans; a one-row prompt and a one-row generated input are structurally identical. Output/logit selection and KV position cannot distinguish their meaning.
- `core_session::allocate` treats MAIN/sequential/n_rows>1 as prefill. The prototype's `!main_prefill` rank binding therefore admits a final prompt row.
- `server_batch::token::is_prompt` already carries the caller's actual role, but `server_context::decode` passes only target-verification intent across `llama_process_ext`. Extended batch entries and `llama_ubatch::data_t::batch_idxs` already preserve row identity through batching/reordering.
- The typed certificate's reserved words must remain zero; weakening that validation or relabeling prompt rows is unacceptable. Disabling approximation for an entire mixed batch would let another request's prompt change a generation row's omission decision.

Proposed minimal full solution: carry optional per-row execution roles through the existing extended-batch and graph-input contracts, with unknown roles exact by default. The server supplies its existing is_prompt information; sampled-input decode is positively known generation; target verification already has trusted speculative intent. Preserve upstream row semantics and all current exact graph behavior. A small dynamic graph metadata input lets prepared programs reuse the same graph when row roles change. Source planning may omit only positively identified generation/verification rows, using per-row roles for independent requests and window-wide best rank only within a known single request. Graph inputs provide owned lifetimes and allocation dependencies instead of a global mutable phase owner or raw reserved pointers. A later upstream phase metadata contract can replace this localized extension.

This extends shared batch/graph contracts beyond the originally planned rank-only change and needs the AGENTS large-pattern design decision before editing. A narrower first pass can restrict omission to already certified single-request target verification, keeping all independent/unknown rows exact; that would leave non-MTP approximation intentionally incomplete. CPU-measured full-work tuning and other-model exact controls can continue independently.
